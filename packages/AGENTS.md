# packages

Shared code. Packages never import an app or a module. Each exposes its TypeScript source from `index.ts` (`main`, or `exports` when it has subpaths), extends `@domus/tsconfig/base.json` and has a `type-check` script; only the apps build. A package with tests adds `test` and a `vitest.config.ts`.

- `platform`: the door (`http`: Better Auth's sign-in and sign-out, the platform's operations such as `password/change` and `sessions/list`, and each module action at `<module>/<action>`, all but `status` only with a session), `identity` (Better Auth, devices, roles, permission rows, each account's delegation table and reading it, passwords and sessions, and the core of `pnpm accounts`: `parseAccountsArguments` and `runAccounts`), `actions` (the one path of every action: `invoke` and `undo`, with a verified context), `authorization` (the only decision: a pure `decide` over roles, permission rows, delegation and areas, ADR 0023), `audit` (the action log over `platform/0001`), `schema.ts` (its `platform_` tables in Drizzle; `pnpm db:generate` writes its migrations from `platform/0002` on, after a base that stands for the hand-written `0000` + `0001` and never runs, ADR 0023), and later jobs, events, notifications and storage. How actions validate, authorize, log, repeat, undo and expire: ADR 0022; a repeat answers an acknowledgement without content (ADR 0023). `@domus/platform/testing` holds what only `test-utils` may import and no production code reaches: a module's raw Drizzle client, a platform with a given clock, synthetic verified contexts, the privileged preparation of accounts, permission and delegation rows, the real read of a delegation table, and the action log as read-only data (ADR 0021, ADR 0022, ADR 0023). Another authorizer is only for platform's own tests.
- `platform/contracts` (`@domus/platform/contracts`): the platform's own contracts, such as `status` and `PROTOCOL`. Pure: no Node, no other part of platform. The only part of platform that `web`, `assistant` and `voice-gateway` may import.
- `module-sdk`: the only part of platform a module may use: `defineModule` (areas, tables, migrations, `contract` and `actions`) and `checkModules`; `@domus/module-sdk/db` re-exports what a module needs of Drizzle and adds `moduleTables(id, areas?)`, with `table` and `ownedTable` (owner, visibility and `id` as only key, ADR 0023), and `id()` (ADR 0021); `@domus/module-sdk/contracts`, pure, offers `readAction({ area?, level })` and `writeAction({ undoable, area?, level })` (ADR 0022, ADR 0023). A module gets its database only from a handler's context, with `visible(table)` and `ownership(table)` for its owned tables, built in `platform/authorization`. Until the write capture (ticket 06), `createPlatform` refuses a module with owned tables; tests open them.
- `ui`: the design system, Vue components (phase 2).
- `i18n`: translation runtime and catalogs.
- `utils`: one business-free topic per folder, imported as `@domus/utils/<topic>`. A topic enters when it knows nothing of the business and two places use it; a topic imports another only through a named exception in `.dependency-cruiser.cjs`. Topics: `connection` (connecting, ready, incompatible, with a 10 s limit per check); `program` (port and address reading, the `/health` server, shutdown on signals); `date-time` (`date-fns`, `Intl`) comes in phase 1.
- `test-utils`: what tests use instead of real infrastructure: `createTestPlatform`, a real platform in memory or on a file with the door in process (the only path the rules give the tests of `assistant` and `voice-gateway` to it), with the real authorization, a controllable clock, the privileged `prepare` (accounts, passwords, grants, delegation), `delegation()`, synthetic contexts (`context`, `member`), a cookie-keeping `browser()` for HTTP tests, typed `invoke` and `undo`, and `log()`; later the fake model and fake channel. Only tests import it.
- `api-client`: `clientFor(contract, transport)`, a thin oRPC link. It holds no contract: callers pass theirs. A write's idempotency key goes in the call's context and travels as a header; authentication and retries belong to the caller.

`utils`, `i18n`, `ui` and `api-client` know nothing of platform, its contracts included.

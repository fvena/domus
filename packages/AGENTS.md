# packages

Shared code. Packages never import an app or a module. Each exposes its TypeScript source from `index.ts` (`main`, or `exports` when it has subpaths), extends `@domus/tsconfig/base.json` and has a `type-check` script; only the apps build. A package with tests adds `test` and a `vitest.config.ts`.

- `platform`: the door (`http`: Better Auth's sign-in and sign-out, the platform's operations such as `password/change`, `sessions/list`, `confirmations/confirm` and `/reject`, `proofs/request`, `delegation/read` (a read on the path of the actions, like `log/read`), and `log/read` and `log/undo` (one's own entries only), and the sensitive writes `permissions/set`, `delegation/set`, `sessions/revoke` and `devices/revoke`, the scheduled tasks' `tasks/list` (a read) and the `manage` writes `tasks/setTime`, `tasks/pause`, `tasks/resume` (undoable) and `tasks/launch` (conflict `task-busy` with a run pending or in progress), and each module action at `<module>/<action>`, all but `status` only with a session), `identity` (Better Auth, devices, roles, permission rows, each account's delegation table and reading it, passwords and sessions, and the core of `pnpm accounts`: `parseAccountsArguments` and `runAccounts`), `actions` (the one path of every action: `invoke` and `undo`, with a verified context; when authorization asks for confirmation the operation waits in `platform_confirmations` and answers `CONFIRMATION_REQUIRED`, and `confirm` and `reject` answer it; a sensitive operation, level `manage` or one of the platform's own in `identity/operations.ts`, needs a step-up proof of that exact operation, kept hashed in `platform_proofs` and used in its transaction, else `STEP_UP_REQUIRED`), `authorization` (the only decision: a pure `decide` over roles, permission rows, delegation and areas, ADR 0023), `audit` (the action log over `platform/0001`), `background` (ADR 0025: the engine of jobs in `platform_jobs`, in two lanes, short and maintenance, one at a time each and both at once; a maximum time per job kind aborts its signal, and one that goes on 10 s more is stuck, its lane taken until it ends; a `PermanentJobError` fails at once, any other error is retried from 30 s doubling up to 5 attempts, keeping only its name and code; a job kind's `failed`, when it has one, runs in the transaction of a failure for good (not of a cancellation); `start` recovers what a previous process left running or stuck, and `stop` waits 5 s at most; the scheduler of the platform's tasks at a local time of `Europe/Madrid`, each planned run unique by task and local date in `platform_task_runs`; the daily `cleanup`, in batches of its own transaction, which empties the content of expired log entries and the operation of expired confirmations, deletes the proofs that decide nothing and old jobs (30 days) and runs (90 days), and never changes an answer; the settings of the tasks as platform operations in `background/operations.ts`, whose changes wake it only after the action's transaction; the watcher, `health()`, which the door adds to `/health` as `background`: `status` `ok` or `degraded`, `reasons` only when degraded, every one at once in a fixed order (`scheduler-silent`: no wake for more than 5 min, it wakes at least every minute; `lane-stuck`; then the backups' `backup-stale`, `backup-retention-failed`, `backup-check-failed`), and `backups` always (`off`, `none-yet`, `none` once an attempt failed with none saved, `saved`); it waits only through the platform's clock and timer; `apps/api` starts it with `startBackground` and stops it with `stopBackground` before `close`, which throws while it is active; module-sdk exposes none of it and a dependency rule keeps modules out), `backups` (ADR 0026: on only with `backups` among the options of opening, a repository and a password file; the daily `backup` at 05:00 in the maintenance lane empties the staging folder `backup-staging` of the data folder, takes `db.backup()` there as `domus.db` with its capture instant, runs `quick_check` in a child Node process and saves that one file with restic, a child process with `--no-cache`, host `domus`, the capture as its time, and the repository and password only in its environment, after `unlock`, initializing only an empty destination; then `forget --prune`, 7 daily, 4 weekly, 3 monthly, grouped by host, waiting up to 10 min for a lock (`--retry-lock 10m`), so only a lock still held after that fails the retention; restic's code 3 (partial) and any but 11 (locked, passing) fail at once with the step and the code, and a failed retention fails the run without a retry, the backup saved; the weekly `backup-check`, Sunday at 05:30 in the maintenance lane, runs `unlock` and `check --read-data`, ends well without touching its mark while the repository does not exist, retries a live lock and marks the check failed on any failure for good, used-up retries included; a timed-out or stopped job aborts `db.backup()` from its progress callback or sends its child SIGTERM and, 5 s later on the platform timer, SIGKILL, settling only once the child ended; the one row of `platform_backup_marks`, loaded at opening and kept in memory, feeds the watcher; restoring, `backups/restore.ts` with `restore.mjs`'s core in `backups/command.ts`, checks the modules as opening does, holds the exclusive lock, prepares the snapshot in `restore-staging` (restic, `quick_check`, the migrator's check and missing migrations, then in one transaction jobs pending, running or stuck cancelled `discarded by restore` with their runs, next runs from now, every session, pending confirmation and proof ended, the provenance and a newer saved mark), closes it in `DELETE` mode and installs it: `before-restore-<instant>` of hard links, the marker `restore.pending` published atomically, the old `-wal` and `-shm` removed, the rename, the marker removed, every step synced; a marker found resumes from removing the auxiliaries, and opening refuses with `restore incomplete: run restore again` or `restore marker unreadable`; module-sdk exposes none of it and a dependency rule keeps modules out), `lock.ts` (ADR 0026: the lock of the database, an SQLite file `domus.lock` in `DELETE` mode beside `domus.db`, never replaced nor deleted; opening on a file holds it shared, a real read taken before touching the data and freed by `close` or a failed open; restoring takes it exclusive without waiting, else `the database is in use: stop api and accounts first`; opening while it is exclusive fails with `restore in progress`; in memory there is none; inside a process only SQLite may open that file, since closing any other descriptor of it drops the process's `fcntl` locks; module-sdk exposes none of it and the backups' dependency rule keeps modules out), `schema.ts` (its `platform_` tables in Drizzle; `pnpm db:generate` writes its migrations from `platform/0002` on, after a base that stands for the hand-written `0000` + `0001` and never runs, ADR 0023), and later events, notifications and storage. How actions validate, authorize, log, repeat, undo and expire: ADR 0022; a repeat answers an acknowledgement without content (ADR 0023). `@domus/platform/testing` holds what only `test-utils` may import and no production code reaches: a module's raw Drizzle client, a platform with a given clock, synthetic verified contexts, the privileged preparation of accounts, permission and delegation rows and sessions, the real request of a step-up proof, the real read of a delegation table, and the action log, the stored pending confirmations and the log of task runs as read-only data, and the background's controlled timer, extra test tasks, synthetic job kinds of either lane and their jobs as data, wake and settle, restoring with a given clock, restic and the cut points of its exchange (only here), the listing of snapshots and the backups' marks as data, and `startChild`, a child process run through tsx that holds the platform open, the exclusive lock or a restore stopped at a cut point over a data folder, tells the test once it holds it and waits for SIGKILL (ADR 0021, ADR 0022, ADR 0023, ADR 0025, ADR 0026). Another authorizer is only for platform's own tests.
- `platform/contracts` (`@domus/platform/contracts`): the platform's own contracts, such as `status` and `PROTOCOL`. Pure: no Node, no other part of platform. The only part of platform that `web`, `assistant` and `voice-gateway` may import.
- `module-sdk`: the only part of platform a module may use: `defineModule` (areas, tables, migrations, `contract` and `actions`) and `checkModules`; `@domus/module-sdk/db` re-exports what a module needs of Drizzle and adds `moduleTables(id, areas?)`, with `table` and `ownedTable` (owner, visibility and `id` as only key, ADR 0023), and `id()` (ADR 0021); `@domus/module-sdk/contracts`, pure, offers `readAction({ area?, level, alwaysConfirm? })` and `writeAction({ undoable, area?, level, alwaysConfirm? })` (ADR 0022, ADR 0023). A module gets its database only from a handler's context, with `visible(table)`, `ownership(table)` and, for the referential block of ADR 0024, `editable(table)` and `forbidden()` for its owned tables, built in `platform/authorization` (`editable` from the same rule as the write capture). Every write to an owned table passes the write capture (`platform/actions/capture.ts`, its rules in `platform/authorization/writes.ts`): temporary triggers, created after the migrations, note each row transition, checked before commit.
- `ui`: the design system, Vue components (phase 2).
- `i18n`: translation runtime and catalogs.
- `utils`: one business-free topic per folder, imported as `@domus/utils/<topic>`. A topic enters when it knows nothing of the business and two places use it; a topic imports another only through a named exception in `.dependency-cruiser.cjs`. Topics: `connection` (connecting, ready, incompatible, with a 10 s limit per check); `program` (port and address reading, the `/health` server, shutdown on signals); `date-time` (`date-fns` with `@date-fns/tz`: the next daily or weekly occurrence of a local `HH:MM` in a given zone, with the rules of the change of the clocks, and the local date of an instant).
- `test-utils`: what tests use instead of real infrastructure: `createTestPlatform`, a real platform in memory or on a file with the door in process (the only path the rules give the tests of `assistant` and `voice-gateway` to it), with the real authorization, a controllable clock, the privileged `prepare` (accounts, passwords, grants, delegation, sessions), `delegation()`, `requestProof`, `setPermission`, `setDelegation`, `revokeSession`, `revokeDevice`, `hasSession`, synthetic contexts (`context`, `member`), a cookie-keeping `browser()` for HTTP tests, typed `invoke` and `undo`, `confirm`, `reject` and `pendingFrom` for pending confirmations, `readLog` (the real read of one's annotations), `log()` and `pendingConfirmations()`, and `background` (the same engine and scheduler on the test clock: `start`, `stop`, `runDue`, `settled`, `runs()`, `tasks()`, `pause`, `resume`, `setTime`, `enqueue`, `flush`, `jobs()`; moving the clock wakes what falls due, unless moved with `{ wake: false }`, a silent scheduler; option `tasks` declares test tasks and `jobs` synthetic jobs the test ends with its own promises), and option `backups` on a file (a temporary repository and password file and, only here, the path of the restic executable), with `background.marks()`, and `restoreBackup` and `listBackups` over the same file and repository, restoring at an instant of the test clock and, only here, with cut points; its tests run the real restic, and a global setup fails the run with `restic is required: brew install restic` without it; later the fake model and fake channel. Only tests import it.
- `api-client`: `clientFor(contract, transport)`, a thin oRPC link. It holds no contract: callers pass theirs. A write's idempotency key and a sensitive operation's step-up proof go in the call's context and travel as headers; authentication and retries belong to the caller.

`utils`, `i18n`, `ui` and `api-client` know nothing of platform, its contracts included.
